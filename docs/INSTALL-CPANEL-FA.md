# نصب آزمایشی بدون Terminal

این راهنما برای بسته اجرایی schema 7 است. رزرو عمومی و شرایط ضبط بسته می‌مانند و نصب ابتدا باید آزمایشی باشد. دیتابیس و ریشه‌های سایت موجود را جایگزین نکنید.

## ۱. آماده‌سازی محیط آزمایش

در cPanel دو دامنه آزمایشی با Document Root مستقل برای سایت و مدیریت تعیین کنید. استفاده از دامنه آزمایشی موجود فقط بعد از اطمینان از خالی بودن و تعلق آن به همین پروژه انجام شود؛ دامنه‌های دیگر حساب در تصویر، خودکار به این پروژه اختصاص داده نشده‌اند. یک پوشه خصوصی مانند `morshed-core-stage` بیرون از **تمام** ریشه‌های وب بسازید.

پیش‌نیاز دامنه‌ها: PHP 8.2 یا بالاتر و `pdo_mysql`. نسخه PHP 8.4.25 اعلام‌شده در phpMyAdmin، نسخه قطعی دامنه‌های شما نیست. نسخه مؤثر را در MultiPHP Manager/Select PHP Version بررسی کنید. cURL و اتصال HTTPS خروجی هنگام اتصال واقعی TSMS لازم‌اند؛ وجود آن‌ها در phpMyAdmin، وجودشان در PHP دامنه را اثبات نمی‌کند.

برای هر دو دامنه SSL معتبر فعال کنید. خاموش بودن «Force HTTPS Redirect» در تصویر، به‌تنهایی نبود گواهی SSL را اثبات نمی‌کند. خود برنامه درخواست HTTP عمومی را نمی‌پذیرد و به X-Forwarded-Proto دلخواه اعتماد نمی‌کند. اگر هاست TLS را پشت پراکسی خاتمه می‌دهد و PHP علامت معتبر HTTPS ندارد، تنظیم صحیح میزبان لازم است؛ bypass در کد انجام نشود.

## ۲. دیتابیس مشترک آزمایشی

از MySQL Database Wizard یک دیتابیس **جدید و خالی** و کاربر اختصاصی بسازید و دسترسی لازم به همان دیتابیس بدهید. هیچ دیتابیس موجود دیگر را انتخاب نکنید.

در phpMyAdmin همان DB آزمایش را انتخاب و فایل `morshed-core/database/install-new-database.sql` را فقط برای DB تازه Import کنید. این فایل حاصل migrationهای 001 تا 007 به‌ترتیب است. فایل جدول‌های این نسخه را می‌سازد و داده نمایشی یا مدیر با رمز پیش‌فرض وارد نمی‌کند. آن را دوباره روی دیتابیس نصب‌شده import نکنید. نام و اثرانگشت migration در manifest بسته قابل بررسی است. هر جدول و اتصال برنامه صریحاً utf8mb4 است؛ نیازی به تغییر charset کل سرور نیست.

اطلاعات «Localhost via UNIX socket» و بدون SSL در phpMyAdmin مربوط به اتصال محلی دیتابیس است، نه HTTPS سایت. اتصال PHP می‌تواند از localhost/socket مجاز هاست استفاده کند. استفاده از اتصال دیتابیس راه‌دور در این بسته فرض نشده است.

## ۳. آپلود بخش‌ها

- محتوای `morshed-core` را در پوشه خصوصی هسته آزمایشی قرار دهید.
- محتوای `morshedapp.ir` را فقط در ریشه سایت آزمایشی و محتوای `admin.morshedapp.ir` را فقط در ریشه مدیریت آزمایشی قرار دهید.
- در آخر هر `index.php`، مسیر require را به فایل ثابت و واقعی `bootstrap.php` هسته آزمایشی تنظیم کنید؛ برای مثال `/home/CPANEL_USER/morshed-core-stage/bootstrap.php`. نام CPANEL_USER و مسیر را از File Manager خودتان بگیرید، نه از نام کاربر موقت phpMyAdmin که ارسال کرده‌اید.
- فایل‌های tests، tools، docs، SQL و تنظیمات خصوصی را در هیچ ریشه عمومی آپلود نکنید. پوشه `storage/sessions` باید برای PHP قابل نوشتن و بیرون وب باشد؛ برنامه آن را می‌سازد. permission 777 لازم نیست.

در چیدمان نهایی که سه پوشه sibling با نام‌های بسته هستند، require پیش‌فرض کار می‌کند. برای محیط آزمایشی با نام هسته یا عمق دیگر، مسیر ثابت دو ورودی باید اصلاح شود؛ این مسیر از URL گرفته نمی‌شود.

## ۴. تنظیمات خصوصی

از `config/local.example.php` یک `config/local.php` در همان پوشه خصوصی بسازید.

- environment را `staging` بگذارید.
- origins.site و origins.admin را آدرس HTTPS دقیق دو دامنه آزمایشی، بدون اسلش آخر، قرار دهید.
- DSN، نام کاربری و رمز DB آزمایش را وارد کنید. نمونه: `mysql:host=localhost;dbname=USER_TESTDB;charset=utf8mb4`.
- ابزار `tools/create-keys-offline.html` را روی رایانه خودتان باز کنید. app_key، کلید نصب و hash کلید را بسازید؛ app_key و hash را در تنظیمات خصوصی قرار دهید. خود کلید نصب فقط در فرم راه‌اندازی استفاده می‌شود.
- setup.enabled را فقط برای راه‌اندازی اولیه `true` کنید. sms.enabled و sms.https_post_confirmed خاموش بمانند.
- allow_http_loopback در هاست همیشه false باشد؛ حالت testing مخصوص آزمون خودکار محلی است.

برای گوگل/ایتا نیز enabled و live_verified پیش‌فرض false بمانند؛ تا تنظیم و آزمون واقعی، فعال نشوند.

هیچ فایل تنظیمات پرشده، رمز، کلید نصب یا توکن را در چت یا مخزن قرار ندهید. app_key را پس از بهره‌برداری ثابت و در پشتیبان خصوصی نگه دارید؛ تغییر آن challengeهای موجود را نامعتبر می‌کند.

## ۵. اولین مدیر

در دامنه آزمایشی مدیریت مسیر زیر را باز کنید:

```text
https://ADMIN_STAGING_DOMAIN/index.php?r=%2Fsetup
```

کلید نصب، نام، شناسه لاتین مدیر و رمز حداقل ۸ نویسه را خودتان وارد کنید. رمز حداکثر ۷۲ بایت است؛ برای رمزهای فارسی طول بایت با تعداد نویسه متفاوت است. این محدودیت از قطع خاموش ورودی توسط bcrypt جلوگیری می‌کند.

پس از ثبت، setup در DB برای همیشه قفل می‌شود؛ دو درخواست هم‌زمان نمی‌توانند دو مدیر اولیه بسازند. در فایل خصوصی setup.enabled را false و token_sha256 را خالی کنید. سپس از `/index.php?r=%2Flogin` با اعتبارنامه اختصاصی مدیریت وارد شوید. همان رمز و نشست، مجوز سایت اصلی ایجاد نمی‌کند. مدیر اولیه شماره همراه تأییدشده ساختگی ندارد.

بعد از فعال‌سازی واقعی پیامک، مدیر اولیه می‌تواند در «امنیت حساب مدیریت» با رمز اختصاصی مدیریت و اثبات پیامکی، شماره خودش را به همان حساب داخلی وصل کند. سپس ورود پیامکی سایت همان user_id را استفاده می‌کند و حساب تکراری نمی‌سازد. این تأیید، نشست مدیریت را به نشست سایت تبدیل نمی‌کند. اگر شماره از قبل متعلق به حساب دیگری باشد، اتصال با خطای تعارض متوقف می‌شود؛ ادغام خودکار نداریم.

اگر کلید نصب را از دست دادید، فقط پیش از اولین مدیر می‌توانید از طریق فایل خصوصی و دسترسی واقعی File Manager، کلید تصادفی تازه تعیین کنید. بعد از ساخته شدن مدیر، کلید جدید قفل DB را باز نمی‌کند. بازیابی اضطراری مدیر بعد از نصب هنوز در این نسخه ساخته نشده است.

## ۶. آزمون پذیرش روی هاست

ورود مدیریت، نمایش داشبورد، رد ورود از دامنه سایت، خروج امن و قفل setup را بررسی کنید. برای حساب‌های سایت، بدون فعال‌سازی واقعی پیامک، حساب ساختگی نسازید و phone_verified_at را دستی پر نکنید. جریان OTP به‌صورت خودکار در تست محلی اجرا شده، ولی دریافت پیامک واقعی روی هاست هنوز آزمون نشده است.

در صفحه تنظیمات مدیریت، وضعیت TSMS خاموش بماند. نام کاربری/رمز/خط ارسال باید فقط در فایل خصوصی وارد شوند. راهنمای `TSMS-FA.md` قرارداد و آزمون‌های باقی‌مانده را توضیح می‌دهد. هیچ مقدار الگو یا پاسخ موفقی حدس زده نشده است.

## Cron

Cron Jobs در هاست شما موجود است. فایل maintenance، bucketهای منقضی rate limit، وضعیت انقضای رزرو/پیشنهاد و state/assertionهای منقضی هویت خارجی را مدیریت می‌کند؛ آرشیو، پیام یا سابقه حسابرسی را حذف نمی‌کند. از رابط Cron Jobs، با **مسیر PHP مناسب همان نسخه که هاست اعلام می‌کند** و مسیر خصوصی واقعی، فایل `morshed-core-stage/bin/maintenance.php` را مثلاً هر پنج دقیقه اجرا کنید. مسیر PHP فرضی در راهنما به‌عنوان مسیر قطعی هاست شما ارائه نشده است. خروجی به فایل عمومی redirect نشود.

صحت محدودیت، انقضای OTP و نشست به اجرای Cron وابسته نیست؛ در هر درخواست بررسی می‌شوند. اعلان تغییر رزرو درون سامانه ثبت می‌شود؛ کد یادآوری یک ساعت پیش از جلسه در maintenance اضافه شده و اجرای خودکار آن به تنظیم Cron وابسته است. تحویل پیامک جلسه هنوز فعال نیست.

## پشتیبان، بازگردانی و ارتقا

قبل از هر تغییر، export دیتابیس آزمایشی، پوشه خصوصی و assets همان نسخه را نگه دارید؛ تنظیمات و کلیدها جدا و با دسترسی محدود باشند. برای بازیابی، یک DB خالی تازه بسازید، export همان نسخه را وارد و config کپی آزمایشی را به آن وصل کنید. پیامک هنگام بازیابی خاموش بماند. نمایش تعداد کاربران و نسخه قوانین و امکان ورود را دوباره بررسی کنید.

در ارتقا، هسته و هر دو ورودی باید متعلق به یک نسخه باشند. برنامه نسخهٔ ۶ را در دورهٔ ارتقا و نسخهٔ ۷ را پس از ارتقا می‌پذیرد. نصب دارای نسخهٔ ۶ فقط از دکمهٔ به‌روزرسانی داخل پنل مدیر اصلی یا migration شمارهٔ 007 استفاده کند؛ راهنما در UPDATE-03-FA.md است. اگر بسته هویت قبلی با schema 1 نصب شده، فقط 002، 003، 004، 005، 006 و 007 را به‌ترتیب Import کنید؛ 001 یا install-new-database.sql را روی آن وارد نکنید. برای نسخه میانی فقط migrationهای بالاتر از MAX(version) نصب شوند. روی دیتابیس قدیمی نامشخص SQL اجرا نکنید. تغییرات DDL MySQL را دارای rollback تراکنشی فرض نکنید. این نسخه migration ارتقا از محصول قدیمی یا ابزار انتقال داده ندارد. backup/restore هاست واقعی هنوز آزمایش نشده است.

پس از restore و پیش از بازکردن دسترسی، نشست‌ها و کدهای OTP snapshot قبلی را در **دیتابیس بازیابی‌شده** باطل کنید تا نشست قبلاً لغوشده دوباره زنده نشود:

```sql
UPDATE m_auth_sessions SET revoked_at=UNIX_TIMESTAMP() WHERE revoked_at IS NULL;
UPDATE m_otp_challenges SET consumed_at=UNIX_TIMESTAMP() WHERE consumed_at IS NULL;
```

پشتیبان خصوصی شامل هش رمز و اطلاعات کاربران است؛ آن را فایل عمومی یا پیوست چت نکنید. پشتیبان تولید را بدون محدودسازی دسترسی و ناشناس‌سازی، به محیط آزمایشی عمومی منتقل نکنید.


## بررسی اختیاری PHP مؤثر هر دامنه

از `tools/check-host.php.example` یک کپی موقت با نام دلخواه و پسوند php بسازید. یک کلید تازه با ابزار آفلاین بسازید؛ فقط hash آن را در expected_sha256 و زمان انقضای حداکثر ۱۵ دقیقه آینده را در expires_at قرار دهید. روی هر Document Root آزمایشی یک‌بار با HTTPS باز، کلید را در فرم وارد و نتیجه را بخوانید؛ سپس هر دو کپی موقت را حذف کنید. فایل پیش‌فرض با hash خالی قابل استفاده نیست. کلید را در URL نگذارید. probe نه phpinfo است و نه اسرار یا مسیر خصوصی را نمایش می‌دهد. خروجی probe هر دامنه را جدا بررسی کنید.

## فایل و دوام پیام

پوشه‌های خصوصی `storage/files` و `storage/content-files` نیز باید برای کاربر PHP قابل نوشتن و خارج از وب باشند. پشتیبان آنها باید با snapshot دیتابیس هماهنگ باشد؛ DB به‌تنهایی فایل‌ها را بازسازی نمی‌کند. فضای هاست برای رشد آرشیو بررسی شود. ورودی سرور باید upload_max_filesize حداقل 5M و post_max_size حداقل 7M داشته باشد؛ نمونه user.ini فقط راهنماست و اثرکردن آن باید در تنظیمات دامنه بررسی شود. فایل‌های اجراشدنی، SVG و HTML پذیرفته نمی‌شوند.

برای نوشتن جلسه، مقدار `SELECT @@GLOBAL.innodb_flush_log_at_trx_commit;` باید 1 باشد. اگر هاست اجازه/تنظیم لازم را ندارد، با پشتیبانی میزبان پیگیری کنید؛ محدودیت در کد دور زده نشود. این بررسی، تأیید سیاست نگهداری یا سرویس ضبط نیست.

## بازگردانی state خارجی

در DB بازیابی‌شده، علاوه بر ابطال نشست و OTP، جریان‌های نیمه‌تمام خارجی snapshot را نیز ببندید:

```sql
UPDATE m_external_flows SET consumed_at=UNIX_TIMESTAMP() WHERE consumed_at IS NULL;
```

جدول identity_assertions را برای بازکردن replay پاک نکنید. پیش از بازکردن دسترسی، قفل انتشار شرایط ضبط و رزرو عمومی را دوباره بررسی کنید. نسخه حاضر مسیر بازکردن این دو قفل ندارد.
