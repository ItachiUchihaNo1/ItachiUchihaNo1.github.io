# انتشار خودکار گیت‌هاب روی cPanel

از این نسخه، فایل `.github/workflows/deploy-cpanel.yml` با هر push مرتبط روی شاخهٔ main و نیز با Run workflow اجرا می‌شود. سورس PHP همچنان روی cPanel اجرا می‌شود. این فرایند به Terminal یا SSH هاست نیاز ندارد.

## تنظیم یک‌باره

در Settings → Secrets and variables → Actions مخزن، سه Repository secret بسازید:

| Name | مقدار |
| --- | --- |
| DEPLOY_FTPS_HOST | cp173.mihanvps.com |
| DEPLOY_FTPS_USER | نام کاربری کامل حساب مخصوص FTP در cPanel |
| DEPLOY_FTPS_PASSWORD | رمز همان حساب FTP |

اتصال TLS سرور cp173.mihanvps.com روی پورت 21 بدون ارسال نام کاربری یا رمز، در این محیط بررسی و گواهی آن تأیید شد. رمز را در سورس، چت یا تصویر قرار ندهید. این سه مقدار، اطلاعات حساب گیت‌هاب یا دیتابیس نیستند.

Directory حساب FTP باید Home مرشد باشد؛ پوشه‌ای که سه پوشهٔ `morshed-core`، `morshedapp.ir` و `admin.morshedapp.ir` در آن وجود دارند. اگر حساب را محدود به public_html یا یک پوشهٔ خالی کرده‌اید، با آن حساب انتشار کامل ممکن نیست؛ مسیر حساب را از cPanel اصلاح کنید یا حساب مخصوص را با مسیر درست بسازید. رمز فقط در GitHub Secrets ذخیره می‌شود.

مقادیر پیش‌فرض Variables عبارت‌اند از `DEPLOY_FTPS_PORT=21` و `DEPLOY_FTPS_BASE=/`. اگر FTP ابتدا Home را نشان می‌دهد، همین مقادیر کافی است. اگر اتصال به پوشهٔ بالاتری باز می‌شود، DEPLOY_FTPS_BASE را فقط به مسیر واقعی مشترک این سه پوشه تغییر دهید. این متغیر نمی‌تواند محدودیت Directory یک حساب FTP را دور بزند.

## مشاهدهٔ نتیجه

Actions → Deploy Morshed to cPanel → آخرین اجرا. برای تکرار دستی، Run workflow را روی main بزنید. مرحلهٔ Upload باید موفق شده باشد؛ پیام انتظار برای Secrets به معنای انتشار موفق نیست.

پس از موفقیت، `https://morshedapp.ir/_release.json` شناسهٔ commit نصب‌شده و نسخهٔ ساختار دیتابیس را نشان می‌دهد. این فایل هیچ راز یا اطلاعات کاربری ندارد. صفحهٔ اصلی و ورود و همچنین بایت‌های CSS و JavaScript از طریق HTTPS بررسی می‌شوند. سبزبودن بخش آزمون بدون اجرای Upload، تأیید نصب روی هاست نیست.

## روش انتقال و حدود دسترسی

- فقط PHP و فایل‌های عمومی متعلق به سه پوشهٔ مرشد منتقل می‌شوند.
- فایل `config/local.php` خوانده، دانلود یا جایگزین نمی‌شود. پوشه‌های storage، config، database، .deploy و فایل‌های محیطی از برنامهٔ انتقال کنار گذاشته شده‌اند.
- عملیات SQL، حذف اطلاعات کاربران، پاک‌سازی آرشیو و حذف فایل‌های نامرتبط انجام نمی‌شود. schema جدید بالاتر از ۶، تا بررسی و نصب دستی migrationها، انتشار را متوقف می‌کند.
- پیش از جایگزینی، همهٔ فایل‌ها در `morshed-core/.deploy/<release>/stage` قرار می‌گیرند و با SHA256 بازخوانی و تطبیق داده می‌شوند. نسخهٔ قبلی کد در همان مسیر خصوصی، زیر backup نگهداری می‌شود.
- فایل عمومی با 644 و پوشهٔ عمومی لازم با 755 منتشر می‌شود. فایل‌های سورس PHP هسته با تأیید صریح مالک، برای سازگاری با اجرای PHP هاست 644 منتشر می‌شوند؛ فایل خصوصی local.php و داده‌ها همچنان از انتقال و تغییر مجوز کنار گذاشته شده‌اند. فایل‌های کنترلی استقرار در پوشه‌های خصوصی 700 نگهداری می‌شوند. این مجوزها صریح‌اند و از ویژگی فایل Windows به ارث نمی‌رسند.
- از این نسخه به بعد، هنگام فعال‌سازی کد، نشانگر خصوصی maintenance پاسخ موقت 503 می‌دهد. پس از انتقال کامل، نشانگر برداشته می‌شود و آزمون HTTP انجام می‌شود. در نخستین انتقال از bootstrap قدیمی، آن bootstrap هنوز نشانگر را نمی‌شناسد؛ از موفقیت همین نصب به بعد این حفاظت نیز فعال است.
- شکست انتقال یا آزمون HTTP، بازیابی فایل‌های همان انتشار را آغاز می‌کند. آزمون‌های خودکار این رفتار را با FTP آزمایشی پوشش می‌دهند؛ قطع خود runner یا اتصال می‌تواند بازیابی دستی را لازم کند. این فرایند جای پشتیبان کامل هاست و دیتابیس را نمی‌گیرد.
- TLS و اعتبار گواهی الزامی‌اند؛ اتصال FTP بدون رمزگذاری یا نادیده‌گرفتن گواهی انجام نمی‌شود. حساب FTP باید مجوزهای استاندارد MLSD، انتقال، rename و SITE CHMOD را داشته باشد.

## اگر اجرا متوقف شد

- تنظیمات اتصال ناقص: نام سه Secret را دقیق بررسی کنید.
- خطای ورود یا مسیر: نام کاربری FTP را کامل وارد کنید و Directory حساب را بررسی کنید. پیام FTP_ROOT_MISMATCH به معنای نامناسب‌بودن Home حساب است.
- خطای TLS: نام سرور و گواهی را از پشتیبانی هاست بگیرید؛ اعتبارسنجی TLS را خاموش نکنید.
- خطای 403 فایل‌های assets: مجوز فایل‌های عمومی باید 644 و پوشهٔ assets باید 755 باشد. اگر این مجوزها درست‌اند ولی 403 ادامه دارد، محدودیت WAF/هاست باید از طرف میزبان بررسی شود.
- اگر انتشار قطع شد و سایت در حالت به‌روزرسانی ماند، ابتدا آخرین اجرای Actions و فایل‌های خصوصی stage/backup را بررسی و نسخهٔ کامل قبلی را بازیابی کنید. سپس فایل `morshed-core/.deploy/maintenance.json` را از File Manager حذف کنید. قبل از بررسی کامل فایل‌ها نشانگر را حذف نکنید.

پشتیبان‌های کد در مسیر خصوصی نگه داشته می‌شوند؛ پس از اطمینان از انتشار و داشتن پشتیبان مستقل، نسخه‌های قدیمی را از File Manager مدیریت کنید تا سهمیهٔ هاست پر نشود. برای توقف انتشار خودکار، workflow را از Actions غیرفعال کنید. تغییر سورس را به شاخهٔ main فقط زمانی بفرستید که انتشار آن روی هاست موردنظر است.

## نتیجهٔ آزمون این تغییر

انتشار خودکار فایل‌های `.htaccess` در ریشهٔ دو دامنه را جایگزین نمی‌کند، زیرا cPanel ممکن است انتخاب نسخهٔ PHP را در همین فایل‌ها ذخیره کند. بستهٔ نصب اولیه همچنان این فایل‌ها را دارد. تغییر قواعد این فایل‌ها در نصب موجود باید جداگانه و با حفظ تنظیمات PHP هاست انجام شود. آزمون مستقل، نبود این دو مسیر در فهرست انتقال و رد ارسال مستقیم آنها پیش از هر تغییر روی هاست را بررسی می‌کند؛ تعداد آزمون‌های انتشار اکنون ۱۲ مورد است.

۱۱ آزمون مستقل مسیرها، حذف اسرار از برنامهٔ انتقال، مجوزهای عمومی، حفظ local.php، بازیابی پس از شکست HTTP، بازیابی پس از قطع rename، توقف روی مسیر اشتباه و نشانگر قدیمی موفق شدند. آزمون اجرای واقعی GitHub Actions و انتقال با حساب FTP کاربر باید جداگانه در Actions تأیید شود؛ ساخت فایل workflow به‌تنهایی به معنای نصب روی هاست نیست.

منابع: https://docs.cpanel.net/cpanel/files/ftp-accounts/ و https://docs.github.com/en/actions/reference/security/secrets

## ترمیم انتشار قطع‌شدهٔ ۲۰۲۶/۱۰/۱۷

اجرای اول پس از رفع مشخصات حساب FTP، به سقف ۱۵ دقیقه‌ای workflow خورد و پیش از تأیید نهایی قطع شد. سقف زمان به ۳۰ دقیقه تغییر کرد و بررسی تکراری پوشه‌های یکسان در هر اتصال حذف شد. شمارندهٔ فایل‌های مرحله‌بندی و فعال‌سازی در لاگ نمایش داده می‌شود.

مالک صریحاً اجازه داد فقط همین نصب قطع‌شده با حفظ پشتیبان‌ها تکمیل شود و مجوز سورس‌های PHP به 644 تغییر کند. برای همین مورد، DEPLOY_RECOVER_COMMIT در workflow فقط به commit قطع‌شدهٔ d6c7d91208bac5ded226248d6e5ab906b6d4b6ec محدود است. محتوای نشانگر باید دقیقاً با همان commit برابر باشد؛ دادهٔ خراب، نشانگر ناشناخته یا commit دیگر همچنان انتشار را متوقف می‌کند. هیچ مجوز کلی برای بازیابی انتشارهای ناشناخته ایجاد نشده است.

فایل local.php و پوشهٔ storage خوانده یا منتقل نمی‌شوند؛ کد ترمیم به لاگ خصوصی هاست نیز دسترسی ندارد. آزمون‌ها علاوه بر حفظ اسرار و بازیابی شکست، پذیرش فقط commit مورد تأیید، رد نشانگر دیگر و حذف درخواست‌های تکراری بررسی پوشه را کنترل می‌کنند. موفقیت واقعی نصب باید از نتیجهٔ Actions و پاسخ سایت بررسی شود، نه صرفاً از ثبت این تنظیمات.
